# Specification Traceability Matrix

**Date:** 2026-08-18
**Scope:** Per-*normative-rule* traceability for `libipynb`'s implementation of the Jupyter notebook
format — nbformat v3 (read-only) and v4.0 through v4.5, plus JEP 62 (mandatory cell IDs, introduced at
v4.5) — and the explicit version-conversion rules the library implements between those minor versions.

**Relationship to the capability audit:** this document is a reformatting exercise, not a fresh
investigation. It decomposes `plans/forensic-capability-audit-2026-08-18.md` (hereafter "the audit") —
specifically its §4 Architecture/API Inventory, §5 Capability-Width Map, and §6 Capability-Depth Matrix —
down to the level of individual normative rules (one schema field, one conversion step, one JEP 62
constraint per row) rather than whole capability areas. Where a row corresponds directly to something the
audit rated, the **Status** column below translates the audit's D0–D5 depth scale as follows, stated once
here and applied consistently:

| Audit depth | Status here | Meaning |
|---|---|---|
| D0 (absent) | `ABSENT` | Confirmed not implemented |
| D1 (surface only) | `THIN` | Exists but effectively untested or only trivially checked |
| D2–D3 (happy path / functional) | `PARTIAL` | Works for the common case; known gap(s) documented |
| D4–D5 (production hardened / independently verified) | `COMPLETE` | Hardened and independently verified |
| — | `BLOCKED_EXTERNAL` | Correct behavior is blocked by an external constraint (e.g. Windows toolchain), not a code defect |
| — | `UNKNOWN` | No citable file/test found for this exact rule; a follow-up is named rather than a guessed status |

Several rows below cover ground the audit did **not** rate at this granularity (e.g. an individual schema
field's presence, or a specific lifecycle conversion step) — for those, Status reflects this document's own
direct inspection of the cited schema/code/test, not an audit translation, and is noted as such inline.

**Primary normative source used throughout:** the six vendored schema files under
`src/libipynb/validation/schemas/nbformat.v4.{0..5}.schema.json`. Per the audit (§3), these were
independently confirmed byte-identical (mod CRLF) to the schemas shipped inside the installed `nbformat`
5.10.4 package — i.e. this repository's vendored copies, not a fresh network fetch, are the correct
normative reference for what this codebase actually targets. JEP 62 (the cell-ID proposal that became
nbformat 4.5) has no vendored text file in this repo; its rule content is read directly off the v4.5
schema's `cell_id` definition and off `model/editor.py`'s independent runtime check.

**Spot-check disclosure:** before finalizing this matrix, 10 rows were independently re-verified by
opening the cited file and confirming the named symbol/logic exists at approximately the cited location
(not merely trusting the audit's or this document's own paraphrase). The 10 rows spot-checked were
`REQ-SPEC-SCHEMA-001`, `REQ-SPEC-SCHEMA-008`, `REQ-SPEC-SCHEMA-011`, `REQ-SPEC-JEP62-001`,
`REQ-SPEC-JEP62-002`, `REQ-SPEC-CONV-001`, `REQ-SPEC-CONV-002`, `REQ-SPEC-CONV-003`,
`REQ-SPEC-CONV-008`, and `REQ-SPEC-CONV-009`. Findings from each spot check are noted inline in that
row's Gap/next action or Test/evidence cell. One correction surfaced by the spot check itself:
`REQ-SPEC-CONV-009` and the pre-4.5 diff/merge blocker under `REQ-SPEC-CONV-010` were both found, on
direct inspection of current `HEAD` (`88aa112`), to already be fixed by commits *after* the audit's
audited revision (`4fdb295`) — the audit's own D2/BLOCKER ratings for those two items are therefore
superseded by newer, in-repo regression tests, and this is called out explicitly in those rows rather than
silently inheriting a stale rating.

## How to read this table

- **Requirement ID** — stable identifier, grouped by area: `REQ-SPEC-SCHEMA-*` (per-version structural
  schema rules), `REQ-SPEC-JEP62-*` (mandatory cell ID rules), `REQ-SPEC-CONV-*` (explicit
  upgrade/downgrade conversion rules), `REQ-SPEC-VALID-*` (cross-cutting validation-oracle rules).
- **Format version(s)** — which nbformat major.minor version(s) the rule applies to.
- **Normative source** — the vendored schema file (with the exact JSON pointer/field where practical), or
  JEP 62 for cell-ID rules not expressible in a v4.4-and-earlier schema.
- **Affected public API/CLI** — the library entry point(s) a caller would actually hit.
- **Implementation file/symbol** — where the rule is enforced, generated, or consumed.
- **Test/evidence location** — the specific test function(s)/file(s) exercising the rule, if any.
- **Oracle + expected comparison** — what independent reference (real `nbformat`, `git`, hand-derived
  schema reading) the row's correctness claim rests on, and what agreement was found.
- **Status** — per the mapping above.
- **Gap/next action** — what's missing, if anything, and what would close it.
